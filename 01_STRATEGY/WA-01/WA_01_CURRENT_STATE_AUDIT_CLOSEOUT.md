## Accepted Carry-Forward Findings

### CF-01 — Astro/PHP deployment and staging drift
Severity: MAJOR

Current deployment/staging documentation does not yet provide a complete,
verified operating procedure for the active Astro static output plus PHP
contact runtime.

Legacy WordPress/theme/SFTP material remains present.

This does not block WA-01 acceptance.

It must remain visible until resolved before an appropriate future
release/deployment gate.

### CF-02 — MicroGrow publication-state conflict
Severity: MAJOR

MicroGrow currently has conflicting public publication-state signals.

Its route/data is PUBLIC-ENABLED while visible project information states:

PENDING OWNER REVIEW

This does not block WA-01 acceptance.

It must be corrected through a controlled public-status/content decision before
a future public change or release.

### CF-03 — Journal / Knowledge / creator/product readiness
Severity: CURRENT-STATE BOUNDARY

Journal, Public Knowledge, Practical Guides, Conscious Living and Digital Product
areas contain useful structures or readiness foundations but are not yet live
publishing, commerce, fulfilment or customer-delivery systems.

No future work may treat readiness architecture as implemented customer capability.

### CF-04 — Bounded named systems
Severity: PUBLIC-BOUNDARY CONTROL

BioCalm, MicroGrow AI Lab, Field Scanner, New Earth Living, GAIA, NEOS,
Platform Core and related named systems must retain their current
evidence-based website classifications unless separately verified.

Website work must not promote contextual or future work into public product,
project or operational capability by inference.

### CF-05 — Governed publishing architecture
Severity: OPERATING BASELINE DEPENDENCY

The current website provides a capability foundation for future governed
publishing.

It does not establish:

- canonical programme sources
- canonical project sources
- canonical product sources
- research authority
- publishing orchestration ownership
- Knowledge / Librarian publishing authority
- GAIA publishing authority
- NEOS publication-state authority
- Platform Core publishing contracts
- Command Centre approval authority
- marketing automation authority
- direct programme-state integration
- autonomous publication

These remain PROVISIONAL or AWAITING BASELINE unless confirmed elsewhere
through accepted New Earth Operating Baseline evidence.

## Governed Publishing Principle

CANONICAL SOURCE
→ PUBLICATION CANDIDATE
→ TOOL / AI ASSISTED PREPARATION
→ RULE / PRIVACY / CLAIM CHECKS
→ HUMAN REVIEW
→ APPROVAL
→ WEBSITE RECORD
→ BUILD
→ STAGING / PREVIEW
→ FINAL APPROVAL
→ PUBLISH
→ VERIFY

Automation prepares.

Human authority publishes unless explicit future governance permits otherwise.

## Future-Build Capability Rule

During the next website release, where an agreed feature or quality requirement
depends on a missing supporting capability, the programme may create the
necessary supporting artefact as part of the governed build.

This may include, where justified:

- visuals
- governed public assets
- Astro components
- content schemas
- data models
- validation scripts
- PowerShell tooling
- publication workflows
- preview tooling
- deployment tooling
- staging controls
- documentation
- tests
- evidence and receipt mechanisms

This rule does NOT authorise uncontrolled scope expansion.

Any new capability must:

1. be necessary for the agreed website release;
2. fit the existing WA governance sequence;
3. reuse existing assets/capabilities before rebuilding;
4. respect public/private boundaries;
5. respect Operating Baseline ownership;
6. avoid becoming a competing source of programme truth;
7. be tested and evidenced;
8. remain human-governed where publication or public claims are involved.
